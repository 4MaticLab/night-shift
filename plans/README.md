# Plans 维护规范

## 文件命名

计划使用 `plans/NNNN-short-name.md`。编号按创建顺序递增，完成或取消后也不复用。索引中的显示名称使用双链，例如 [[plans/0003-mvp-quality-hardening]]。

## 状态

- `proposed`：已记录但未批准，不自动进入实现。
- `approved`：范围与验收已确认，可以开始。
- `in_progress`：正在执行；仓库同时只保留一个主计划为此状态。
- `blocked`：存在明确外部阻塞，必须记录解除条件。
- `completed`：全部验收条件满足并留下验证证据。
- `cancelled`：明确不再执行，保留原因以避免重复提案。

## 推进模式

- `auto`：仓库内、可回滚、已有目标范围内且无外部副作用的改进。范围、验收、验证和依赖明确后，代理可以自行批准并连续推进。
- `manual`：涉及产品方向、外部发布或消息、权限、付费资源、破坏性迁移、用户数据或其他需要新授权的工作。

推进模式不会绕过状态流转；`auto` 计划仍需从 `proposed` 进入 `approved`，开工前再进入 `in_progress`。

## 进度规则

任务列表是进度的事实来源，[[PLANS]] 中的 `x/y` 必须与勾选项一致。任务完成代表有可检查的产物，不代表“开始过”。范围变化应写入决定记录；新增范围较大时拆成新计划。

## 计划模板

```markdown
# NNNN — 计划标题

- 状态：`proposed`
- 优先级：P1
- 创建：YYYY-MM-DD
- 更新：YYYY-MM-DD
- 负责人：Codex / Human
- 依赖：无
- 推进模式：`auto`

## 动机

为什么值得做，以及当前证据。

## 范围

- 本计划会改变什么。

## 非目标

- 明确不做什么。

## 任务

- [ ] 可验证任务一
- [ ] 可验证任务二

## 验收标准

- 用户或工程层面的完成条件。

## 验证

- 命令、测试或人工检查。

## 决定记录

- YYYY-MM-DD：创建提案。

## 相关文档

- [[docs/index]]
```

## 生命周期操作

创建、批准、开工、阻塞、恢复或完成计划时，都要在同一变更里更新 [[PLANS]]。稳定事实发生变化时再同步 `docs/`；计划中的设想不能提前写成已实现事实。
