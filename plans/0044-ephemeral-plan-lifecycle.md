## 动机

仓库进入多人并行开发后，永久递增编号、全局唯一 `in_progress` 和完成后继续保留计划文件会造成主线冲突、索引膨胀与计划目录长期增长。计划的主要价值发生在施工期间；完成后的稳定事实应进入 `docs/`，过程证据可以由 Git 提交历史保留。

## 范围

- 把复杂任务计划改为以分支为边界的临时文件，不再使用全局递增编号。
- 要求复杂任务第一笔提交先提交完整计划，施工期间同步更新。
- 验收完成后、创建 PR 前删除计划及活动索引项，并单独提交退役记录。
- 允许不同主题分支各自拥有 `in_progress` 计划。
- 明确计划可追溯所需的合并策略与 Git 查询方式。
- 更新代理手册、计划规范、文档指南与决策记录。

## 非目标

- 本次不批量删除 0001–0043 既有历史计划或改写所有旧文档反链。
- 不改变代码评审、测试门禁或外部发布授权。
- 不把微小修复强制升级为复杂任务计划。

## 任务

- [x] 创建计划并作为分支第一笔提交。
- [ ] 定义复杂任务与临时计划命名、状态、并行及提交规则。
- [ ] 更新 AGENTS、PLANS、文档指南与 ADR。
- [ ] 验证双链和规范一致性。
- [ ] 把稳定事实沉淀后删除本计划及活动索引项，作为 PR 前最后一笔提交。

## 验收标准

- 新任务不依赖全局编号，也不要求全仓库只有一个 `in_progress`。
- 复杂任务在实现前有可审核的计划提交；完成后主线不新增永久计划文件。
- Git 历史中仍能找回计划正文、进度和退役记录。
- squash 不会被误用于依赖已删除计划历史的 PR。
- 旧计划保持可读，新规则不会制造断链。

## 验证

- `npm run docs:check`
- `git diff --check`
- 检查开工计划提交与计划退役提交均存在
